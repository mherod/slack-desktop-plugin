## Why an AX-focused field may still fail

Chromium separates an element’s focused state from page/widget focus. [`Document::SetFocusedElement`](https://github.com/chromium/chromium/blob/156.0.8078.49/third_party/blink/renderer/core/dom/document.cc#L6073) dispatches `focus` and `focusin` only while the page’s focus controller is focused. An element-state change therefore does not alone prove that a component’s focus handlers ran.

The ordinary [`HandleCharEvent` path](https://github.com/chromium/chromium/blob/156.0.8078.49/third_party/blink/renderer/core/frame/web_frame_widget_impl.cc#L1407) uses the focused-or-main frame and lacks the particular widget-focus gate used for IME commits. [`WidgetBase::ImeCommitText`](https://github.com/chromium/chromium/blob/156.0.8078.49/third_party/blink/renderer/platform/widget/widget_base.cc#L1702) returns early for untargeted input when IME handling is disallowed; a main-frame widget’s [`ShouldHandleImeEvents`](https://github.com/chromium/chromium/blob/156.0.8078.49/third_party/blink/renderer/core/frame/web_frame_widget_impl.cc#L4467) requires `HasFocus()`. This permits different ordinary-character and multi-unit IME outcomes. It does not prove that Slack took this early return during the observed run.

The native [`RenderWidgetHostViewMac::Focus`](https://github.com/chromium/chromium/blob/156.0.8078.49/content/browser/renderer_host/render_widget_host_view_mac.mm#L666) returns immediately when its view is already first responder. Otherwise it requests the responder transition; [`OnFirstResponderChanged`](https://github.com/chromium/chromium/blob/156.0.8078.49/content/browser/renderer_host/render_widget_host_view_mac.mm#L2001) propagates gained focus only under specified headless, explicit-focus or key-window conditions. Repeatedly setting the same web field focused is not a demonstrated reset of page focus.

Apple’s installed `AXAttributeConstants.h` explicitly permits setting `AXFocused` only to true, not clearing it with false. The pinned [Chromium web accessibility setter](https://github.com/chromium/chromium/blob/156.0.8078.49/ui/accessibility/platform/browser_accessibility_cocoa.mm#L954) likewise ignores false. Read-only local AppKit disassembly found the NSView false path reporting an illegal value, its true path requesting `makeFirstResponder:`, and NSWindow focus reporting unsettable. No setter was executed during that AppKit inspection, and notification observers were not comprehensively traced.

Together these findings support a possible focus-state mismatch. They do not establish its exact cause in Slack, or equate an AX value echo with the application’s search state.

## Pointer delivery and rendering evidence

Electron 45.1.0 contains the [external posted-click fix](https://github.com/electron/electron/blob/v45.1.0/patches/chromium/fix_deliver_clicks_that_another_process_posts_to_a_background_app.patch#L36). Read-only inspection of Slack’s installed binary also confirmed the corresponding inactive-app/external-source-PID branch. Its [upstream regression](https://github.com/electron/electron/blob/v45.1.0/spec/api-browser-window-posted-click.spec.ts#L71) uses always-on-top windows and checks mouse-down delivery, not editable-field focus; it cannot substitute for Slack’s after-state proof.

The [injector fixture](https://github.com/electron/electron/blob/v45.1.0/spec/fixtures/native-addon/mouse-input/src/post_to_window_mac.mm#L12) uses window-number NSEvents posted directly to the process. Chromium’s receiving [coordinate conversion](https://github.com/chromium/chromium/blob/156.0.8078.49/components/input/web_input_event_builders_mac.mm#L135) and [native hit-test](https://github.com/chromium/chromium/blob/156.0.8078.49/content/app_shim_remote_cocoa/render_widget_host_view_cocoa.mm#L1028) use the delivered `locationInWindow`. A locally correct CG screen position does not prove the final widget hit.

AX press is not merely a click without down/up: the pinned [accessibility simulation](https://github.com/chromium/chromium/blob/156.0.8078.49/third_party/blink/renderer/core/dom/events/event_dispatcher.cc#L118) dispatches pointer-down/up and, unless prevented, mouse-down/up before click. Its path still differs from coordinate-based native hit-testing and caret placement.

Occlusion remains an unproven explanation for stale pixels. Electron documents [macOS occlusion affecting page visibility](https://github.com/electron/electron/blob/v45.1.0/docs/api/browser-window.md#L116), while Chromium’s [accessibility lifecycle update excludes paint](https://github.com/chromium/chromium/blob/156.0.8078.49/third_party/blink/renderer/modules/accessibility/ax_object_cache_impl.cc#L981). AX changes and unchanged screenshots can coexist. Working background global Search also means the observations do not establish that all JavaScript stopped.

## Accepted route and remaining verification

The earlier bounded native-focus inspection found no usable exposed reset: the web area and seven inspected ancestors did not expose a usable `AXFocusableAncestor`, and the inspected standard window buttons reported focus unsettable. Those results remain historical limits on the attempted focus route. The successful clipboard/Shift-Insert mechanism does not require resolving that theory or repeating its focus experiments. Input remains withheld whenever exact query focus, window/workspace identity or popup ownership is unverified; a composer is never a fallback target.

The supported sequence establishes a fresh Home → DMs view, preserves workspace and unread state, presses the exact query, then pastes through scoped Shift-Insert. Real editor content and the supported autocomplete list establish query acceptance together. Candidate option keys are positional observations within that query, not conversation IDs. People can be directory matches without existing DMs; group names do not establish full membership. `--pages=N` (1–10) bounds autocomplete collection and deduplicates overlapping option observations, retaining distinct same-name groups and unknown completeness on no progress.

Temporary clipboard use was explicitly authorized for development. The reusable command requires `--allow-clipboard` for nonempty search and `read-dm group-name:EXACT_NAME`; explicit `dms --search=` clears through the fresh-view path without clipboard access. The clipboard protocol preserves available item/type data within bounds, checks change count and payload ownership before paste/restoration, and avoids restoring over a detected newer copy. Public `NSPasteboard` has no atomic compare-and-swap, so simultaneous copy/paste activity can race the checks or observe temporary content. Guarded best-effort restoration is the claim; atomic invisibility or guaranteed preservation under every interleaving is not.

An exact group-name read performs a fresh query and requires one exact supported group option before selection. It verifies the canonical C/G conversation URL, DM title and group message list before returning messages, then emits ordinary `group:ID` continuations. Ambiguity withholds selection. A list of suggestions alone is not proof that this complete read path or every output format has passed. Record fresh bundled acceptance separately from probe evidence and synthetic extraction tests.

Fresh group reading also established that Home can restore a previously open conversation. The reader now derives the selected group's canonical ID before Home recovery, solely from timestamp permalinks corroborated by direct message-row IDs in the unique exact-name group-direct-message list, excluding threads. It then calls the existing ID-bound group reader and rechecks the canonical URL, name and typed list. The [native workflow acceptance record](native-workflow.md#direct-dms-search-acceptance--10-november-2026) records successful bounded search collection and a two-page group read; it makes no all-format or complete-directory claim.

## Success Criteria

- [ ] A fresh bundled `dms --search=TEXT --allow-clipboard` run verifies the real editor query and supported autocomplete results, with `dms-search-autocomplete` coverage; an AX value echo or the underlying recent list alone is insufficient.
- [ ] Query/result identity and unchanged workspace/unread state survive requested `--pages=N` (1–10); deduplication retains distinct positional candidates, and no progress leaves completeness unknown.
- [ ] A no-match query has an independently verified explicit empty-result structure; a missing, loading or unsupported list cannot establish zero results.
- [ ] Acceptance probes retain the same foreground app and pointer samples and never send input to a composer, with before/after evidence and explicit sampling limits.
- [ ] Clipboard opt-in, bounded preservation, ownership-change refusal and restoration outcomes are verified without logging clipboard contents or claiming atomic concurrent-use guarantees; explicit clearing needs no clipboard.
- [ ] Exact group-name reading requires fresh unique group evidence, verifies the canonical destination before messages and emits ID-bound continuations; ambiguity remains unselected.
- [ ] Fresh text, JSON and full-JSON commands agree on verified matches and coverage; local filtering remains separate and no final test or delivery status is inferred from the probe alone.
