# Text and JSON output

The Bun entrypoint defaults to trimmed plain text. Use the bundled wrapper: direct Swift execution produces the internal accessibility receipt instead.

| Option | Output |
|---|---|
| Default, or `--format=text` | Readable listings, messages, search snippets or a current-view summary; saves report the destination, byte count and SHA-256; `inspect --ui` selects concise diagnostic hierarchy |
| `--format=json` | Full captured semantic text/metadata or a verified save receipt; `inspect --ui` and after-error observations include their bounded diagnostic nodes, without desktop samples |
| `--format=full-json` | Native diagnostic receipt(s), including captured accessibility nodes, before/after observations and desktop samples; saves also retain selected download/publication evidence and wrapper resolution |

Formats apply to every command, including `read-thread`, permissions and native error receipts. The format only affects output, not the selected interaction mode. JSON opt-ins do not fetch additional content.

`close-members` returns the verified channel and whether its Members dialog was open and closed. No dialog is an explicit no-op. Text stays concise; JSON retains the same outcome, and full JSON additionally retains the native before/after identity and desktop samples. A failure preserves `closeMayHaveBeenRequested` and `dialogMayBeOpen`, including unknown values. A Close press alone never counts as verified closure. This command reads no member names and accepts no target, workspace, foreground or pagination flags.

```sh
bun "$SKILL_DIR/scripts/slack.mjs" channels
bun "$SKILL_DIR/scripts/slack.mjs" channels --pages=3 --format=json
bun "$SKILL_DIR/scripts/slack.mjs" dms
bun "$SKILL_DIR/scripts/slack.mjs" dms --pages=3 --format=json
bun "$SKILL_DIR/scripts/slack.mjs" dms --filter='Alex Example' --pages=3 --format=json
bun "$SKILL_DIR/scripts/slack.mjs" dms --filter=
bun "$SKILL_DIR/scripts/slack.mjs" dms --search='Alex Example' --allow-clipboard --pages=3 --format=json
bun "$SKILL_DIR/scripts/slack.mjs" dms --search=
bun "$SKILL_DIR/scripts/slack.mjs" read-channel 'team-updates'
bun "$SKILL_DIR/scripts/slack.mjs" read-channel '#team-updates'
bun "$SKILL_DIR/scripts/slack.mjs" read-dm 'Alex Example'
bun "$SKILL_DIR/scripts/slack.mjs" read-dm '@alex.example'
bun "$SKILL_DIR/scripts/slack.mjs" read-dm '@alex.example' --allow-clipboard --pages=3 --format=json
bun "$SKILL_DIR/scripts/slack.mjs" read-dm 'group:C012EXAMPLE' --pages=3
bun "$SKILL_DIR/scripts/slack.mjs" read-dm --allow-clipboard 'group-name:Exact observed group name' --pages=3
bun "$SKILL_DIR/scripts/slack.mjs" read-thread 'C012EXAMPLE:1700000000.000001'
bun "$SKILL_DIR/scripts/slack.mjs" save-media 'F012EXAMPLE' --output='/absolute/existing-directory/attachment.bin' --format=json
bun "$SKILL_DIR/scripts/slack.mjs" save-media 'F012EXAMPLE' --original --output='/absolute/existing-directory/attachment.bin' --format=json
bun "$SKILL_DIR/scripts/slack.mjs" read-channel 'team-updates' --pages=3
bun "$SKILL_DIR/scripts/slack.mjs" read-thread 'C012EXAMPLE:1700000000.000001' --pages=2 --format=json
bun "$SKILL_DIR/scripts/slack.mjs" search 'requested terms' --pages=3 --format=json
bun "$SKILL_DIR/scripts/slack.mjs" channels --format=json
bun "$SKILL_DIR/scripts/slack.mjs" --format=full-json inspect
bun "$SKILL_DIR/scripts/slack.mjs" inspect --ui --filter=c-virtual_list --limit=60 --depth=30
bun "$SKILL_DIR/scripts/slack.mjs" inspect --ui --filter=Query --format=json
bun "$SKILL_DIR/scripts/slack.mjs" inspect --ui --prepare --format=json
```

These are alternatives; run the requested command. Format flags may precede or follow the command. Duplicate/unknown formats are usage errors before any Slack interaction. Use `--` before a literal flag-like argument, for example `search -- '--format=json'`; it then remains query text. Channel names accept letters, numbers, hyphens and underscores, with an optional leading `#`. DM names and handles are exact and case-sensitive. Without `--allow-clipboard`, ambiguous or unmatched DM queries withhold Return and return available candidates inline. With the flag, a verified zero-exact-match normal lookup can use direct DMs search; exact duplicate matches and guard/navigation failures still stop. Use an observed handle from candidate output or `inspect`. Group DMs use the exact `group:CONVERSATION_ID` action emitted by `dms`, scoped to the current workspace. The `group:` and `group-name:` prefixes are reserved. Follow an offered `read-dm --allow-clipboard group-name:EXACT_NAME` action for fresh exact-name discovery; arbitrary member-name fragments are not navigation targets.

## Default text

Interaction defaults to background. Add `--interaction=foreground` to an interacting command for an explicit foreground fallback, including with pagination and any output format. It may bring Slack forward once, leaves focus where it is, and never automatically retries a failed command. Text appends one concise foreground notice. JSON adds `interaction` describing activation evidence independently of operation status; full JSON also keeps diagnostic PIDs and samples. Pure `inspect`, `read-media`, `permissions` and help reject foreground mode. Emitted navigation hints remain background by default, so each intended foreground invocation needs its own flag.

Channel and DM listing text shows up to 30 conversations total per command, including with `--pages=N`; it labels omitted rows and points to JSON for every selected record. A DMs local filter selects matching records from the verified collection before this display cap. Conversation/thread text shows up to ten messages/replies per logical page, with at most 500 characters of body text per message plus bounded media metadata lines. `read-channel` defaults to three pages (up to 30 messages), including continuations; DM and thread reads default to one page; `--pages=N` collects up to ten pages and displays every selected record, at most 100 messages/replies. Initial channel/DM reads select the last ten loaded messages; initial thread reads select the first ten loaded replies and keep the root separate. Search defaults to the first ten snippets in text and all captured matches in JSON. Multi-page search text shows the first `10 × completedPages` unique matches in Slack's result order, explicitly labels omitted matches, and points to JSON for all collected matches and their full captured text. Output retains observed authors/times, source links and short coverage notes. Text shortening is labeled; format flags themselves do not fetch more content. Other commands' JSON retains all captured entries. No original message is changed. Missing metadata is labeled as not exposed. Terminal controls in UI text are removed for display; JSON preserves the captured strings.

`inspect` summarizes the current conversation/search view, or the open Query box and its suggestions. `search` shows the submitted query, observed result/page counts and snippets. Use `inspect --ui` for bounded structural/capability inspection and `--format=full-json` for the original native receipt.

`channels` reads the currently exposed sidebar, including channels in custom sections. It excludes individual and group DMs and combines duplicate channel IDs. When Search covers the sidebar it closes a verified Query overlay with targeted Escape or uses the identified Home tab's AXPress action. If the sidebar does not appear, it stops. Without `--pages`, or with `--pages=1`, it retains the original single capture without scrolling. Larger page budgets collect downward sidebar captures as detailed below. No channel is opened or joined, no section is expanded, and no filter is changed. Captures do not enumerate the entire workspace directory.

`dms` without `--search` opens or reuses Slack’s recent DMs view and optionally pages downward from its verified list position. It can list one-to-one, group and self conversations absent from Home’s sidebar. `--filter=TEXT` performs a local literal case-insensitive substring match over observed conversation names and explicit participant-header labels after verified collection and deduplication. An omitted or empty filter imposes no local restriction. Slack’s own search text and unread toggle remain unchanged; text distinguishes those observed controls from the local filter and reports matches within the collected records. The helper does not open conversations, join anything or reset the list. Semantic listing records omit message previews; full JSON retains the exposed raw diagnostic tree. Text labels group DMs and self conversations, and displays only supplied safe `read-dm` actions. The DM listings section below describes when actions are withheld.

Initial channel and individual-DM reads first use the guarded search picker. An ordinary `read-dm NAME_OR_@HANDLE --allow-clipboard` permits direct DMs autocomplete fallback only after a verified normal lookup has zero exact matches. It requires a complete advertised candidate set and one exact person name/handle, then verifies the actual D ID, name and individual-message list before returning messages. Exact duplicate picker matches and arbitrary guard or post-submission failures never authorize fallback; direct search never selects a fuzzy or group match. Lookup uses no message page; explicit cursors remain in the current verified view and never perform discovery. Group-DM reads reuse an exact loaded current group, use its exposed mpim sidebar control, or look up an absent sidebar row by its exact conversation ID. After excluding query/quick-message options, lookup requires exactly one remaining navigation option with the supported group marker, binds it to the exact query, then verifies the final exact ID, DM title and group-direct-message list before extracting messages. It has a 12-second Search lookup deadline and consumes no message pages. Continuations stay in the verified current destination and never rerun discovery. Thread panes, composer content, reactions and controls are excluded from message text. Compact message rows sometimes omit their author. Only structurally linked conversation rows can inherit a sender from the same capture, with an explicit `(inferred)` label; unsupported cases remain `null`.

Output supports progressive reading: a channel row shows `read-channel NAME`; an eligible one-to-one/self DM row shows `read-dm NAME`; a group row shows `read-dm group:CONVERSATION_ID`; a message with an observed reply control shows `N replies · read-thread REF`. These references stay visible even when the displayed message text is shortened. Use the shown reference instead of copying a long URL. Message references are stable conversation/message identifiers, not row numbers, and resolve within the current workspace. Name-based commands still verify the exact destination before input. JSON carries the same actions as `{command, args}` navigation objects; these are helper subcommands, used after `bun "$SKILL_DIR/scripts/slack.mjs"`.

## Compact JSON envelope

The fields below describe ordinary `--format=json` output. Plain text renders a concise view of this data. Direct DMs autocomplete search has the specific record/receipt shape documented under DMs search matches. For a single page, full JSON is the raw diagnostic receipt with its tree under `content.nodes` and/or `before.nodes`/`after.nodes`. With `--pages=N` greater than one, full JSON is an envelope with `operation`, `pid`, `status`, `pages` (the individual raw receipts) and `batch` counts/direction/stop reason. A later native failure adds `error` and `next`; a first-page failure keeps the ordinary error receipt. Full JSON is not the semantic schema below and preserves the native result even if semantic extraction rejects a frame. An explicit DMs local filter adds separate wrapper `selection` metadata after semantic validation, as described under DM listings; it does not remove native captures.

| Field | Meaning |
|---|---|
| `schemaVersion` | `1`; structured commands share this schema version |
| `interaction` | Foreground invocations only: requested mode, activation attempt/observation, state and no focus restoration. An activation request or observed activation is not command success; `unknown` means no usable native evidence survived. Default background output omits this field |
| `accessibilityProbe` | Permission results and failed AX preflights: actual application-read status, checked attributes and exact error code/name/operation where present. Trust alone does not imply access. Semantic JSON omits the native PID; full JSON retains it |
| `permissionScope` | Permission results identify `current-execution-context`: trust, post-event access and AX evidence apply to this invocation. This field neither detects a sandbox nor authorizes host execution |
| `accessStatus` | Failed command preflights distinguish `permission-required` from `unavailable` while retaining `status: stopped`. No command input follows either failure |
| `operation`, `requested` | Command and original requested name/handle/query; `requested` is null for `channels` and `dms` |
| `observedAt` | ISO timestamp for the native capture, or the final verified capture in a collection |
| `workspace` | Observed `name`, URL `contextId`, and `id` only when the context is a workspace ID; enterprise contexts are not relabeled as workspaces |
| `view` | Observed main-window `title` and `url` from the final verified capture; after a partial stop, inspect before assuming the view remains current |
| `coverage` | Scope, observed count, incomplete-history flag, virtualization, capture bounds and warnings. DMs view results add `source: "dms-view"` and native `filters: {query, unreadOnly}`; an explicit local `--filter` adds separate `match` query/field/count/scope evidence |
| `pagination` | Conversation/thread page state with optional `batch` summary and final-view `older`/`newer` actions; channel sidebar or DMs view collection state with direction `down`; or search collection state with direction `next`. Listing/search collections expose no cursor actions. Listing `hasMore` is null; search `hasMore` derives from the final explicitly displayed page count, or is false for verified empty results |
| `navigation` | Supported next actions as `{command, args}` objects; thread results include their reference and a channel backlink when verified |
| `lookup` | Present after successful individual-DM fallback: `{source: "dms-search-autocomplete", query, conversationId, exactMatchCount: 1}`. The original exact name/handle and verified D ID bind this evidence to the requested read; ordinary successful picker reads omit it |

For conversation, channel and DM read/list results, `coverage.complete` is always false. Channel membership has the separate advertised-count contract below. A successful bounded capture (`captureTruncated: false`) means traversal completed within its limits, not that Slack exposed every channel, DM or message. `pagination.hasMore: null` means unknown, not false. Repeating a conversation/thread read without a continuation flag selects an initial page from the current loaded content; use the returned continuation action to advance. Channel listings start at the current Home sidebar position; Ordinary DM listings start at the current DMs view position with its observed controls; explicit DMs search starts from its verified query suggestions. Search uses a fresh verified query submission and actual result-page controls. These collections do not invent continuation cursors. Full JSON retains foreground/cursor samples; these are sampled observations rather than continuous proof.

## Permission results

Permission output is separate from message pagination. `permissions` reports `ready` only when trust, actual Slack AX reads and post-event access all verify; `inspection-only` means actual AX reads work without keyboard access in this execution context. These return exit 0. Missing trust or API-disabled returns `permission-required` with exit 3; unavailable/absent/ambiguous Slack access returns `unavailable` with exit 1. `permissionScope: "current-execution-context"` is retained in JSON and full JSON. False API flags alone do not diagnose a sandbox or globally missing macOS approval. Missing trust leaves `accessibilityProbe.status: "not-checked"`; that is not a Slack API-disabled response.

Text labels a permission-required result as permission required in this execution context, including the missing-trust/not-checked combination, and shows a short `Slack AX` status alongside trust/keyboard evidence. The recovery hint directs the caller to verify approved host execution with read-only `permissions` through the normal tool approval mechanism before recommending macOS settings. It does not authorize automatic escalation, a denied-request bypass, foreground activation or replay of the original operation. Only if access remains missing in the approved context does explicit OS setup become the next step. `permissions --request` remains the explicit prompting command; a successful prompt request is not a grant or readiness proof. An unreadable `inspect --ui` returns a stopped status with the full bounded capture retained in full JSON. UI diagnostic coverage can include sorted `axErrors: [{code, name, count}]`, bounded to sixteen distinct codes and never exceeding the failed-read total.

## Pagination

The cursor and logical-page rules below apply to conversation/thread reads. Sidebar capture collection is described under Channels and DM listings; search result-page collection is described under Search and inspection.

Use the exact `Older`, `Newer` or `More replies` command emitted by a conversation/thread read. The following forms illustrate the syntax; replace the references with observed values:

```sh
bun "$SKILL_DIR/scripts/slack.mjs" read-channel 'team-updates' --before=C012EXAMPLE:1700000000.000001
bun "$SKILL_DIR/scripts/slack.mjs" read-dm 'Alex Example' --before=D012EXAMPLE:1700000000.000001
bun "$SKILL_DIR/scripts/slack.mjs" read-thread C012EXAMPLE:1700000000.000001 --after=C012EXAMPLE:1700000001.000001
bun "$SKILL_DIR/scripts/slack.mjs" read-dm 'Alex Example' --before=D012EXAMPLE:1700000000.000001 --pages=3
```

`--before` selects messages strictly older than its boundary; `--after` selects strictly newer messages. Both are supported for `read-channel`, `read-dm` and `read-thread`, and are mutually exclusive. Timestamps stay strings with ten seconds digits and six fractional digits. The positional thread reference identifies the root; its page reference identifies the already-read boundary. Individual-DM continuation commands use the exact observed display name, even when the initial read used `@handle`; group continuations retain `group:CONVERSATION_ID`. The cursor pins the same conversation ID. Follow the shell quoting in text, or pass the separate JSON `command` and `args` fields as arguments.

Continuations require the same current conversation/thread and an exposed boundary message. They stop before scrolling if those identities changed, the picker is open, or the cursor is stale. Read the destination again for fresh references; the helper does not navigate back automatically. Eligible loaded messages are served without input. If none are available in the requested direction, the helper attempts one background `AXScrollToVisible` action on the identified edge row, waits up to five seconds for progress and requires overlap between the old and new message identities.

Logical pages contain at most ten messages or replies in both text and JSON. Older pages take the ten eligible messages nearest the boundary; newer pages take the first ten eligible messages after it. Results remain chronological, exclude the boundary and preserve distinct messages with identical text. The page cursor is based on returned rows, so text truncation cannot skip hidden messages. Full JSON retains the complete current diagnostic capture, including overlapping or additional exposed rows outside the logical page.

`--pages=N` accepts a canonical integer from 1 to 10 on `channels`, `dms`, `read-channel`, `read-dm`, `read-thread` and `search`. Omitted or `--pages=1` retains single-page behavior and receipt shape. Duplicate, malformed and unsupported uses fail before Slack input. Flags may appear before or after the command; a literal `--pages=...` after `--` remains a target/query string where a target/query is accepted. `channels` and `dms` accept zero positional arguments. Without an explicit boundary, conversation collection proceeds older for channels/DMs and newer for threads. An explicit `--before` or `--after` sets that direction for the whole conversation/thread collection; both flags are rejected for `channels`, `dms` and `search`.

The requested count includes the first logical capture, even if it uses a supplied boundary, and any final no-progress capture. One helper process retains its initial Slack app, workspace, window and foreground guard, verifies each continuation, and stops on the page budget, no progress, no offered continuation, a guard failure or a 60-second collection budget checked before another page. The multi-page wrapper allows 90 seconds for the native process. Collection adds no keyboard or mouse primitive: each page uses loaded content first and at most one existing scoped accessibility scroll.

Collection deduplicates verified message timestamps within the pinned conversation/thread and returns the selected messages in chronological order. Whole records retain their captured metadata and inference provenance; body/author fields are not stitched between captures. The root is retained once if any verified page exposed it. Final-view navigation hints are used rather than synthetic cursors over the aggregate; an opposite-direction command can revisit messages already present in the collection. A partial failure removes both pagination hints.

For conversation/thread reads, the semantic `pagination` object contains:

| Field | Meaning |
|---|---|
| `supported` | `true` for conversation/thread reads |
| `direction`, `cursor` | `older`/`newer` and requested reference, or null for an initial read; collections retain the first page's request |
| `status` | `initial`, `advanced`, or `no-progress`; collections retain the final verified page's state |
| `hasMore` | Always null: viewport progress does not establish the history boundary |
| `older`, `newer` | `{cursor, navigation: {command, args}}` or null; use the offered action while its view remains current |
| `nextCursor` | The requested direction's next reference, or initial older-history/newer-thread reference; null if no action is offered |
| `capturedCount`, `eligibleCount`, `returnedCount` | For one page: snapshot records, records beyond the boundary and returned records. For collections: unique captured records, final page's eligible count and unique selected records returned across all pages. Thread counts exclude the separately retained root |
| `scrollAttempts` | Zero or one per page; the sum across verified pages in a collection |
| `batch` | Present for multi-page collections: requested/attempted/completed counts, direction, stop reason and repeated viewport-record count, detailed below |

`coverage.observedCount` counts returned messages plus an exposed thread root; `coverage.capturedCount` counts verified captured messages, including that root. Conversation/thread collection counts are unique across verified captures. A `no-progress` result adds no messages from its final page, retains earlier collected messages, withholds the same-direction retry hint, and keeps the end of history unknown. It is a successful observation, not proof of an empty conversation or complete thread. A thread may omit a direction when the exposed root/count evidence leaves no further replies in that direction, but `coverage.complete` and `hasMore` retain their conservative meanings.

For all multi-page collections, `pagination.batch` contains:

| Field | Meaning |
|---|---|
| `requestedPages` | Requested maximum number of channel sidebar/DMs view captures, logical conversation/thread captures or actual search result pages, 2–10 |
| `attemptedPages` | Captures attempted, including a later failed attempt |
| `completedPages` | Captures retained after verification, including a final no-progress capture, a channel sidebar capture exposing only DMs or an explicit empty search result frame |
| `direction` | `down` for channel sidebar and DMs view listings; `older` or `newer` for conversation/thread reads; `next` for search |
| `stopReason` | `page-limit`, `no-progress`, `no-next-page`, `error` or `time-limit` |
| `deduplicatedCount` | Conversation listings: repeated channel or DM observations removed across captures, according to the requested command. Conversation/thread reads: repeated verified viewport records. Search: repeated canonical matches. This is output deduplication, with nothing deleted from Slack |

For conversation/thread reads, `capturedCount` can exceed `returnedCount` because each viewport may expose rows outside the selected ten-message page. Conversation listings and search instead count verified observations and unique returned records, as below. A page budget or stop reason does not establish complete history or a complete directory. Text reports collected records and completed pages, labels the stopping condition and labels channel/DM listings or search matches omitted from its concise display.

## Workspaces

`current-workspace` returns `workspace: {name, contextId, id, domain, ref}`. `contextId` is the observed `T…` or `E…` client context; `id` is non-null only for a `T…` context. This inspection does not open a selector, so `domain` and `ref` may be null.

`workspaces` adds ordered `workspaces` records with the same identity fields, `current`, and `navigation: {command: "switch-workspace", args: ["workspace:example.slack.com"]}`. Names and domains come from verified selector rows. Only the current row has a known context ID. `coverage.scope` is `exposed-workspace-switcher` and `coverage.complete` is false; this is not an account directory or invitation inventory. Text shows at most thirty entries, current markers and short switch hints; JSON retains the bounded verified inventory.

`switch-workspace` returns the verified destination in `workspace` and `switch: {requested, attempted, changed, from, to}`. An already-current target has `attempted: false` and `changed: false`. Unknown or ambiguous targets retain their failure status and available candidates. Stopped results preserve `workspaceSwitchMayHaveBeenRequested` as true, false or null, without presenting a stale workspace as verified current. Text shows at most eight candidates and never substitutes DM hints.

All three formats pass wrapper identity/transition verification. Full JSON retains native before/after observations, scoped-selector action evidence and desktop samples, plus semantic `resolution`; a failed resolution cannot become a successful full-JSON result. No workspace IDs, URLs or memberships are inferred from names or domains.

Reads, search, conversation listings and `save-media` accept `--workspace=REF`. Scoped semantic output adds `requestedWorkspace`, nested `workspaceSelection` (the validated switch result) and `workspaceSwitchMayHaveBeenRequested`. The ordinary operation, messages, media, pagination and coverage retain their existing meanings. A successful selection can accompany a failed read, so inspect both statuses. Text adds one workspace line and scopes supported follow-up commands with the verified `--workspace=workspace:DOMAIN`; JSON scopes structured navigation arguments. Scoped attachment-save hints also retain that verified workspace and still require an explicit output path.

Full JSON additionally retains the raw native `workspaceSelection`, fresh `workspaceScope: {contextId, windowId}` and wrapper `workspaceResolution`. Selection precedes the requested action within the same native process and lease. Every exposed source root and page must agree with the selected context; transcript preflight must verify before the wrapper sends an opening token. Missing or inconsistent selection/scope proof cannot bypass validation through full JSON. Permission, cancellation and protocol failures keep false, true and unknown switch outcomes distinct.

For scoped saving, full JSON retains the initial `preflight`, any `sourcePreflight` and `viewerPreflight`, `started`, and the read-only `publicationPreflight` (native phase `publish`). The checkpoint is workspace/Download verification, not filesystem publication; `publication` and `saved` remain the file-artifact evidence. A failure after Download or publication keeps the strongest action uncertainty and any known path, bytes, hash and publication state, with command status `stopped`. Workspace selection success alone cannot turn a failed save into success, and full JSON cannot bypass phase or source validation.

A save setup failure omits any phase that never occurred and retains the workspace selection error and available candidates. Unsupported viewer-modal failures can include `viewerIsolation` in full JSON: a rejection reason, structural-only modal/overlay nodes and explicit capture/field truncation flags. This diagnostic has no action authority and does not appear in concise output.

## Channels

`channels` is an array of `{id, name, url, isPrivate, unread, selected, sections, navigation}`. IDs and names come from sidebar rows. URLs remain null if no link was exposed; privacy is not inferred from an ID prefix. Unread/selected markers are true when observed and otherwise null. `sections` preserves observed sidebar section names. A supported channel name gets a `read-channel` navigation action.

`channels --pages=N` (1–10) accepts no positional target or `--before`/`--after` boundary. The first capture uses the currently exposed sidebar position; omitted `--pages` or `--pages=1` retains the existing single-capture behavior and receipt. Each subsequent capture uses at most one advertised `AXScrollToVisible` action on a verified sidebar edge row, proceeding downward while retaining the app, workspace, window and foreground guard. It does not reset to the top, open or join a channel, expand sections or change sidebar filters.

Progress verification tracks all sidebar conversation rows, including individual and group DMs, but `channels` emits channel records only. A verified capture with only DMs still counts toward the page budget and can continue when its rows advance. `no-progress` means that the bounded attempt did not expose new sidebar rows; it does not prove an endpoint or that every channel was listed. Collapsed sections, filtered-out channels and other unexposed rows remain unknown. `coverage.complete` remains false and `pagination.hasMore` remains null.

Collection deduplicates by workspace and channel ID, keeps the first whole record from verified captures, and preserves sidebar encounter order. It does not merge metadata from later observations. Text reports unique channels across completed sidebar captures and shows at most 30 channels total, with an explicit omitted count and `--format=json` recovery hint. JSON retains every unique collected channel and its navigation action. The full-JSON collection envelope retains individual raw receipts under `pages` plus `batch` metadata.

For a collection, `pagination.supported` is true, `direction` and `batch.direction` are `down`, and `nextCursor` is null; no executable sidebar continuation command is invented. `pagination.capturedCount` and `coverage.capturedCount` sum each verified frame's unique channel observations, excluding DMs. `pagination.returnedCount` and `coverage.observedCount` count unique channels across the collection. `batch.deduplicatedCount` is the difference between those captured and returned counts. `scrollAttempts` sums actions represented by verified captures; a failed transition may have scrolled without producing a frame, so this field does not count every physical input on partial results. `batch.attemptedPages` includes failed capture attempts; `completedPages` counts only verified captures, including DM-only frames.

Sidebar collections stop at the page limit, no progress, a guard failure or the shared 60-second native collection budget; the wrapper allows 90 seconds for the process. A later failure or native time limit returns the verified channel prefix with `status: partial`, an error and inspect-next guidance, and exit 1. No automatic scroll retry follows uncertain input. A first-capture failure remains the ordinary error receipt. A successful bounded stop has `status: ok` and never claims a complete workspace directory.

## Channel members

`members NAME` returns `channel: {name, id}`, the advertised `total`, `members` and `coverage: {scope, complete, collected, pages, maxSeconds, memberFilter, stopReason}`. Each member retains its observed canonical U/W user ID. Separately exposed name/title text produces `{id, name, title?}`. A supported leaf profile button instead produces `{id, name: null, label}`: `label` is the entire observed accessible label, which can include guest markers and profile text. It is never split into an inferred name or title, and no navigation identity is derived from it.

Leaf labels must be nonblank, free of control characters and at most 2,000 Unicode characters. They require a canonical member row, a unique directly owned profile button and a verified empty child inventory. Text explicitly marks `[profile label; name unavailable]`, shows at most 100 members and shortens each profile label to 300 characters with JSON recovery guidance. JSON retains every captured member and the exact accepted label, including its original spacing.

`coverage.complete` is true only when unique captured member IDs reach the channel's advertised count and the native stop reason agrees. This covers that channel's observed membership list; it does not establish workspace-wide discovery or identity from a partial name. Successful output also requires verified closure of the member dialog. A stopped member read can offer `close-members` when its dialog may remain open. `maxSeconds` records the resolved collection deadline (default 160 seconds, or 70 with `--pages`); `--max-seconds=N` accepts 1–900 and retains any page cap. A time-limited partial read suggests the longer bound when available; older receipts without this additive field remain readable. New native reads require the exact All member filter throughout collection and retain `coverage.memberFilter: "All"`; an older receipt without filter evidence leaves that field absent rather than inferring All.

## DM listings

The recent-conversation records below apply when nonempty `--search` is absent. Direct search uses the separate autocomplete match contract below; the source determines how identifiers and navigation hints may be interpreted.

`dms` contains `{id, name, kind, participantLabels, url, handle, unread, selected, sections, navigation}` records. `kind` is `one-to-one`, `group` or `self`, verified from the DMs view row structure rather than an ID prefix alone. `name` is the first direct conversation-title text. `participantLabels` contains only a group's explicit direct static header labels after its title and before the unique metadata container; individual/self rows use `[]`. Those strings are not split into people and do not establish complete membership. Message snippets, nested links and presence metadata cannot supply a name, participant label or handle. Current hub records leave `url` and `handle` null and `sections` empty; unread/selected markers are true when explicitly observed and otherwise null. Listing records contain no messages, presence or inferred handles/membership.

`dms` opens or reuses the verified DMs view and defaults to one capture; `--pages=1` keeps a single capture. `dms --filter=TEXT` applies a literal case-insensitive substring filter locally after verified collection and deduplication, matching each observed conversation name or explicit participant-header label. It does not search messages or infer missing members. Omit `--filter` or use `--filter=` for no local restriction. Local filtering preserves Slack’s search field and unread-only state; explicit `--search` has the separate behavior below. The exact argument accepts at most 200 Unicode characters without C0/C1 control characters; explicit empty remains distinguishable from omission in request metadata. `inspect --ui --filter` instead selects diagnostic nodes; neither flag edits Slack’s search text.

`dms --pages=N` accepts 1–10, with no positional target or `--before`/`--after` cursor, and can be combined with `--filter`. Collection begins at the current verified list position and pins Slack’s exact search-filter value and unread toggle. Each transition uses one supported downward edge-row `AXScrollToVisible`, a pinned workspace/window, the 60-second native budget and 90-second wrapper deadline. Local matches do not change page budgets or progression: collection does not stop at the first match or collect extra pages to fill a result limit. Pages do not reset the list, edit Slack’s filters or select a conversation. The previous edge and common-row order must survive; new rows must appear after the edge. Incoming activity or user changes can invalidate that order and stop collection.

`coverage.source` is `"dms-view"`. `coverage.filters.query` contains Slack’s trimmed observed search query and `unreadOnly` contains the observed boolean; local filtering never changes these fields. Empty observed text and a false unread toggle remain distinct from unknown values, which stop verification. Raw native scope retains the untrimmed `filterValue` and ordered descendant labels in `filterText`, including accessibility whitespace, and verifies both across captures. Nonblank descendant labels must match the trimmed filter value exactly; unrelated text is not accepted as hidden filter evidence. Unsupported query chips or missing filter state stop instead of claiming an unfiltered list. Historical sidebar receipts keep their original source interpretation and wording; the current command does not fall back to sidebar discovery.

An explicit `--filter`, including `--filter=`, adds `coverage.match: {query, fields: ["name", "participantLabels"], observedCount, matchedCount, scope: "captured DM names and observed participant header labels"}`. `query` retains the exact local argument. `observedCount` counts all unique verified DM records before local matching and equals `coverage.observedCount`; `matchedCount` counts the records retained in `dms`. Omission leaves `coverage.match` absent, and top-level `requested` remains null in every case. Text labels the local query and matching counts separately from Slack’s existing query/unread state. Explicit empty matches all observed records and does not clear Slack’s search field.

DM collection deduplicates by workspace and conversation ID, retains the first whole observed record and preserves DMs-list encounter order. Participant labels are not merged across repeated records. A later capture that gives a repeated ID a different name, kind or `participantLabels` array is rejected before any of that capture's records are accepted. Earlier verified records remain as a partial prefix with exit 1 and inspection guidance. Navigation is then checked across the whole retained collection: if distinct IDs share a name, their individual-DM name hints are suppressed, including hints from earlier captures. Group references remain distinct because they use conversation IDs. Local matching follows these checks and cannot conceal a rejected page or make an ambiguous hint safe.

One-to-one/self DMs with a safe unique exact observed name receive `{command: "read-dm", args: [name]}`. Verified groups receive `{command: "read-dm", args: ["group:CONVERSATION_ID"]}`; duplicate group display names remain separately addressable. Empty, unsafe or overlong names, surrounding whitespace, control/formatting characters and individual names beginning with `@` or the reserved `group:`/`group-name:` prefixes receive no name hint. A display name beginning with `@` is not an observed handle. Name uniqueness is checked across all verified captured/collected records before local filtering; filtering cannot restore an ambiguous name hint. The existing `read-dm` exact picker verification still withholds Return if the intended destination is unavailable or ambiguous. Follow the emitted action rather than inventing a name or handle. A local participant match describes only an explicit observed header label, not a complete membership list, participant identity or observed handle; message previews are never matching evidence.

Text shows at most 30 matching DM conversations total for both single captures and collections, labels group DMs and self conversations, and reports any omitted rows with a JSON recovery hint. Collection text summarizes matches within unique observed DM conversations across completed DMs view captures. JSON retains every matching DM record. Without a local filter, all verified records remain selected. Full JSON uses the ordinary single receipt or the multi-page `pages`/`batch` envelope; every hub capture carries `dmPagination.scope.source: "dms-view"`, scope evidence, ordered row keys and extracted DM IDs.

For an explicit local filter, full JSON also includes `selection: {source: "wrapper", mode: "local", status, query, fields, observedCount, matchedCount, matchedIds, scope}`. A validated result uses `status: "ok"` or `"partial"`, and `matchedIds` identifies the selected records from the verified captures. When selection cannot be verified or native capture stops before a usable result, `selection.status` is `"unavailable"` with an error and no invented IDs/counts. The native receipt is retained unchanged alongside this selection metadata; its captured nodes can include rows excluded by the local filter.

DM collection pagination uses `supported: true`, `direction: "down"`, `batch.direction: "down"` and `nextCursor: null`. `capturedCount` sums each verified capture's unique supported DM observations, and `coverage.capturedCount` retains that observation sum. `coverage.observedCount` counts unique DMs before local filtering; `batch.deduplicatedCount` is the observation sum minus that unique count, so excluded local matches are never counted as duplicates. `pagination.returnedCount` counts the selected records after local filtering, equal to `coverage.match.matchedCount` when a filter is supplied. Canonical but unsupported rows remain in paging order and can establish progression, while coverage notes explain their omission from DM records. A missing, empty/loading or entirely unsupported list stops instead of returning a verified empty directory.

`scrollAttempts` counts only transitions represented by verified captures, while `batch.attemptedPages` also includes failed attempts. Stops and partial-result semantics match channel collection; local filtering applies only to the verified prefix, preserving its failure status. `hasMore` remains null and `coverage.complete` remains false: Slack-filtered or unexposed DMs and the full workspace directory remain unknown. Zero local matches can be a successful bounded result when supported records were verified; it does not establish that no matching DM exists outside those records or among unexposed group members. A `no-progress` stop establishes only that the bounded attempt exposed no additional rows in the DMs view. No executable list cursor or automatic retry is invented.

Ordinary name/handle reads accept the same flag for the guarded direct-search fallback; successful normal lookup does not use the clipboard.

Names, handles and group evidence come from each supported option. A positional option key identifies an observation only within the verified query; it is not a Slack conversation ID or permalink. Autocomplete output also retains `workspace: {name, contextId, id}` from the verified canonical DMs view URL. A T-prefixed context supplies `id`; an E-prefixed enterprise context keeps `id: null`. With `--workspace=REF`, that context must match the verified selection before workspace-bound read hints are added. Missing, malformed or different context evidence cannot become successful scoped search output. Workspace identity does not fill the suggestions' unknown conversation IDs.

For a supported custom-named group, `name` is its separately exposed title. The participant subtitle remains private native verification evidence rather than a parsed participant list or handle; public autocomplete fields and unknown existence stay unchanged.

A full diagnostic error receipt may include `namedGroupStructure`: the failed proof stage, predicate booleans and bounded presence/count/result metadata for at most five nodes. It excludes source text, identifiers and URLs. Unknown child counts remain distinct from zero, and explicit absent subroles remain distinct from API failures. Successful output has no such diagnostic field.

An exact group-ID picker refusal can also include `groupPickerState` in the full error receipt. It retains bounded Query values/ranges, supported option labels/classes, selection and advertised-action booleans, and retained-element comparisons from before cleanup. Counts and truncation are explicit. This is private query/destination evidence, not message content, and does not authorize a retry or appear on success.

An observed unique handle can supply a `read-dm '@handle'` action. An eligible exact group name supplies `read-dm --allow-clipboard 'group-name:EXACT_NAME'`. This is a fresh name lookup, not an ID-bound reference. Every advertised ARIA set position must be captured with consistent integer sizes before name selection; unexposed or uncounted candidates require a known group ID: the reader requires a unique exact supported group candidate, selects it once, then verifies its actual C/G conversation ID, DM title and group message list before returning messages. Duplicate exact names withhold selection. After successful reading, continuation hints use `group:CONVERSATION_ID` and ordinary message cursors; they do not replay the name lookup or require clipboard access. JSON keeps actions as separate `{command, args}` values. Follow the emitted quoting/arguments rather than promoting an option index or member-name fragment into a target.

When the hub still exposes `/dms` after selection, the reader obtains the canonical group ID from timestamp permalinks corroborated by direct message-row IDs in the unique exact-name group message list, excluding threads. It then uses the ID-bound group reader and verifies the canonical destination again. Home may restore another conversation, so Home navigation alone never binds the resulting read to the requested group.

`--pages=N` accepts 1–10 autocomplete captures, with the same concise text/JSON/full-JSON choices. It retains query/workspace/list identity through bounded scrolling, preserves result order and deduplicates overlapping positional option observations only within that verified query. Distinct same-name groups are not merged. Changed candidate metadata rejects the affected capture. Text shows at most 30 matches across the collection and labels omissions; JSON retains every verified collected match. Full JSON retains the query/list scope, raw captures and transition/stop evidence; local filtering remains separately labeled wrapper selection.

No progress, the page/time budget or a guard failure stops collection. `hasMore` remains null and `coverage.complete` remains false: this is a bounded suggestion set, not an exhaustive directory or proof that all DMs were found. Missing/loading/unsupported lists cannot establish zero matches; an explicit verified empty-result structure is necessary. A later failure keeps only the verified prefix with exit 1. No executable autocomplete cursor or automatic retry is invented.

Clipboard receipts report preservation/restoration outcomes without original clipboard contents. A detected newer clipboard generation suppresses restoration rather than overwriting it. Public pasteboard ownership checks and writes are non-atomic; simultaneous copying/pasting can race them or observe the temporary query. The output therefore must not describe clipboard use as untouched, invisible or guaranteed atomic.

## Conversation messages

`conversation` contains `{kind, name, id, url, handle}`; group reads additionally expose `dmKind: "group"`. The kind is `channel` or `dm`, verified against the destination title, URL and message-list label. Initial navigation additionally verifies the selected individual/channel suggestion, the exact ID-bound sidebar control, or a group suggestion bound to its exact-ID lookup query. Individual fallback first selects one exact person from complete direct-search candidate evidence and derives the real D ID from that person's typed message pane before Home. It uses that ID's observed individual sidebar control or, only when the row is absent, one freshly observed different `@handle` lookup. The final canonical destination must match the captured D ID and exact name; the original failed query is never replayed. Missing identity or neither supported route leaves a stopped read, even if the DMs view shows the selected person. No URL or ID is synthesized. Group exact-ID lookup remains query-bound and verifies the final destination before messages are returned. For ID-based reads, `requested` retains `group:CONVERSATION_ID`. Exact-name group discovery retains its requested name reference while the verified conversation and continuations use the resulting canonical ID. No lookup query or extra page is inserted into the message result. `handle` is retained when an exact handle selected the individual DM or direct-search fallback exposed one, including across a multi-page collection. A separate continuation command uses the verified current name and ID, or the group reference, and leaves `handle` null.

Each `messages` entry contains:

- `id`: observed message-list identity; identical text with different IDs remains separate.
- `author`: directly observed sender, structurally inferred conversation sender, or null. Inferred values are explicitly marked rather than presented as observed metadata.
- `authorInferred`, `authorSourceMessageId`: present on inferred conversation records as `true` and the original observed sender's message ID. Text appends `(inferred)` to that author's name.
- `displayedDay`, `displayedTime`: labels as Slack exposes them, without guessing dates or time zones.
- `permalink`: observed Slack timestamp link or null; links belonging to a different conversation reject the capture.
- `text`, `links`: body text in accessibility child order and observed body links. Exposed emoji-image labels contribute when Slack's `c-emoji` class identifies the image or its containing emoji group, separated from adjacent prose when needed. No shortcode, glyph or image description is invented. Existing whitespace/punctuation is retained; emoji separation is disabled within inline and block code. Line wrapping/paragraph layout may differ from the visual message.
- `attachments`: observed file/media metadata with short references and `contentRead: false`, detailed below; files are not downloaded, opened or played.
- `previews`: separately captured external link previews, with observed title/description/URL and message-bound references; these are not uploaded-file records.
- `quotedMessages`: separately exposed forwarded/shared message text with its observed `author`, `permalink`, `text`, `links` and `textComplete: false`; quoted content is not attributed to the outer message sender.
- `thread`: displayed reply summary, parsed count when explicit, and `repliesRead: false` for conversation/search reads. When a positive reply count and message permalink are exposed, `ref` and `navigation` provide the supported `read-thread` action. A bare reply link without a reply control does not advertise an unverified opener.
- `textComplete: false`: collapsed, truncated or unsupported rich content may remain outside the exposed text.

Message order follows the exposed main list, or verified timestamp order across collected pages. No thread replies are merged in and no complete-history claim is made. Missing fields stay null. An absent or mismatched message list is an error, not a successful empty conversation. A verified channel accepts Slack's `channel` or `private channel` message-list label while retaining the exact conversation name and canonical-ID checks; the same matching rule applies to readiness and pagination. `read-channel` and `read-dm` wait briefly for identified message rows in the matching main list; if none appear, they report an empty-or-loading limitation rather than asserting that the conversation has no history. An already-open exact channel can be read without navigation. Each full JSON page receipt includes a `recovery` list describing initialization and view recovery; concise output remains focused on the requested content.

Sender inference is limited to the verified main conversation list in one capture. A missing-author row must expose Slack's adjacent compact timestamp inside an `actions--above` message group, following an observed sender with increasing timestamps. Day dividers, unrecognized rows, non-increasing order or a row without grouping evidence reset the inference chain. A directly observed sender starts a new chain. Nothing carries across commands, captures, conversations, threads or search results. Because logical paging follows extraction, the source message can be outside the returned ten-message page while still present in the same diagnostic capture.

## Rich-media metadata and references

Conversation reads, thread roots/replies, search matches and semantic inspection share the same media extraction. It reads the captured accessibility tree without additional Slack input, downloads, playback or transcript generation. These fields extend `attachments[]` while preserving `label`, `url` and `contentRead: false`; the compact envelope remains schema version `1`. Unexposed metadata is null, and transcript availability uses its explicit `unknown` state.

| Field | Meaning |
|---|---|
| `kind` | Media kind supported by observed container/control structure: `image`, `document`, `audio`, `video` or generic `file`; URL suffixes alone do not establish type |
| `label`, `filename` | Observed media label and filename when separately supported; a clip's descriptive label is not necessarily a filename |
| `fileId` | Observed Slack file ID when supported by an unambiguous recognized file URL or ID-bearing control; otherwise null |
| `ref`, `referenceScope` | Short file reference with scope `workspace-file`, or message-bound attachment reference with scope `message-media`; missing identity evidence leaves no usable reference |
| `url` | Retained primary observed link for compatibility; use the named URL fields to distinguish its role |
| `filePageUrl`, `downloadUrl`, `thumbnailUrl` | Distinct observed targets for a Slack file page, Download control and image thumbnail; an absent target remains unknown |
| `fileDetailsAvailable` | Optional true-only capability for a supported source-owned `View file details` button or inline-video `More actions` ellipsis; absent means this capability was not established, and it does not prove that a pane or Download target is available |
| `description`, `descriptionSource` | Exposed image description with source `accessibility`; this is observed text, not helper-generated OCR or visual interpretation |
| `displayedDuration` | Duration as exposed by the player, without guessing a duration from text elsewhere in the message |
| `displayedPlaybackTime` | Exposed elapsed/current playback position, kept separate from total duration; a lone `0:00` is not treated as a zero-length attachment |
| `transcript.state` | `available` for an existing transcript-reading control, `generatable` for a generation control, or `unknown` when availability is not exposed; audio/video records with a valid reference and an existing transcript may offer `transcript.navigation` for `read-transcript` |
| `provenance` | Observed attribution from an enclosing forwarded/shared card, when present; distinct from the outer message sender |
| `contentRead` | Always `false` for this metadata extraction; neither file bytes nor transcript contents were read |

Known file IDs produce short references such as `F012EXAMPLE`, scoped to the current workspace in the output envelope. Without a file ID, a verified source message can produce `C012EXAMPLE:1700000000.000001/m1`. The `/m1` suffix is the captured attachment position, not a durable file ID. It must be revalidated against that message's current media identity and order before any future action. Missing source-message identity leaves the fallback reference null. No raw accessibility node index becomes a reference.

External unfurls appear in `previews[]`, not `attachments[]`. They retain observed `kind`, `title`, `description`, `provider`, `url`, `thumbnailUrl`, `contentRead: false` and a message-bound `/p1` reference with `referenceScope: "message-preview"` where the source message is verified. Unexposed metadata is null. An external video preview does not prove a Slack-hosted upload or a downloadable original. Forwarded media and previews retain observed `provenance: {kind: "quoted", author, permalink}` instead of being attributed to the enclosing message's sender; absent provenance is null. Quoted source text appears separately in `quotedMessages[]`. Source permalinks require an explicit timestamp, permalink or footer control; an arbitrary Slack link in the quoted body is not source evidence.

Attachment references are accepted by `read-media REF` as described below. Preview references remain descriptive only. `read-transcript REF` accepts an audio/video attachment reference when an existing transcript is exposed. `save-media REF --output=PATH` requires a supported Download control belonging to the selected attachment, its verified static-image viewer or its verified file-details pane, as described below. Existing `read-thread`/conversation/search actions and observed message permalinks provide message context. Media references cannot be substituted for a thread reference or `--before`/`--after` cursor.

Default text shows media even when the message has ordinary body text. It renders at most four combined attachment/preview records per message, attachments first, and labels any omitted records. Display labels/titles are capped at 120 Unicode code points, descriptions at 140, durations at 40 and provenance authors at 80; shortened/omitted media points to `--format=json`. Useful observed values appear on compact lines, for example:

```text
Video · demo.mp4 · 4:36 · transcript available · read-media F012EXAMPLE · read-transcript F012EXAMPLE
Image · diagram.png · read-media C012EXAMPLE:1700000000.000001/m2
  Description (accessibility): A diagram showing the service's three components.
```

The example is illustrative, not a captured Slack message. Text shows at most two `Quoted · AUTHOR: TEXT` entries per message, with source authors capped at 80 characters and quoted text at 220; omitted or shortened quotations also point to JSON. JSON retains every media/quoted record on the selected pages and full captured metadata strings; display caps do not change those records. Full JSON remains the original native diagnostics, not this semantic schema. Search highlights are removed from media display labels without rewriting URL or ID values.

Within a message, physical media is extracted from recognized attachment roots rather than counted once for every matching wrapper/header. Message pagination and search aggregation retain their existing whole-record deduplication: references and metadata stay with the chosen message observation, with no field stitching across captures. Sharing the same file in two distinct messages does not merge those messages. More pages may expose additional messages/media, but no format option fetches file contents.

**DO** preserve URL roles and unknown metadata. **DON'T** equate an image link, thumbnail or Download target with verified original bytes, infer MIME type from an extension, or claim transcript content from a control label. **Check:** metadata keeps `contentRead: false`, the availability state matches the observed control, and no additional AX action or network transfer is performed to enrich a read.

## Referenced attachment inspection

`read-media REF` returns the metadata of one currently exposed attachment. Accept an observed `F012EXAMPLE` file ID within the current workspace, or a message-bound reference such as `C012EXAMPLE:1700000000.000001/m1`. Message identifiers start with C, D or G, timestamps retain ten seconds digits and six fractional digits, and attachment ordinals are canonical integers from 1 to 9999. References have at most 256 characters. Preview `/pN` references, message permalinks and malformed references are rejected. The command accepts the ordinary format and lock-timeout options, but no `--pages`, `--before`, `--after`, clipboard or UI-inspection flags.

The reader examines the exposed main conversation or search results and any verified open thread. It captures those sources twice within the pinned workspace, then requires stable attachment identity and order. It neither navigates to a hidden source nor opens a media preview. If a message has left the viewport, use the existing source-reading commands to expose it again.

File IDs resolve from current observed file identity, never a filename match. Repeated observations of the same file retain their source/provenance context; conflicting identity observations stop rather than selecting one silently. Positional references additionally require a remembered binding from a recent successful helper read. That private binding covers the source message and its complete attachment order, so replacing or reordering media does not silently retarget `/mN`. Missing, expired or changed bindings return a stopped result with a source-reread instruction. Neither two captures nor the cache proves that Slack stayed unchanged between observations or after completion.

Compact JSON uses `operation: "read-media"`, `requested`, `workspace`, `view`, a selected `media` attachment record, `sources`, `coverage` and supported `navigation` actions. `sources` retain verified message references, observed permalinks, author, thread information and per-source provenance observations when available. If observed quoted provenance differs between sources, the selected media's singular `provenance` is null and the source records retain those distinctions. Unknown metadata stays null. `media.contentRead` and `coverage.contentRead` remain false, and coverage is explicitly limited to exposed metadata. `coverage.referenceBinding` distinguishes `current-workspace-file` from `remembered-message-order`.

Default text expands the selected attachment's useful metadata with bounded labels, description, duration, transcript availability, observed URL roles and source hints. JSON retains full captured metadata. Full JSON retains both native observations and the wrapper's `resolution`; reference verification and the success/stopped exit status apply to every format. Selecting full JSON does not bypass a stale-reference guard. No format reads original bytes, interprets image pixels or obtains transcript contents.

`read-media` can offer `save-media REF --output=PATH` for a supported observed Download target, a known image file with a canonical private-file source URL eligible for viewer inspection, or a known document/file, audio or video attachment with `fileDetailsAvailable: true` and no exposed Download URL. `PATH` is a placeholder for the requested file destination, not a suggested filename. The details capability is a mutable observation, separate from attachment identity; it neither supplies a missing file ID nor overrides a changed reference. The save command independently revalidates the source and raw Download inventory before input; a hint does not promise that the viewer or pane will expose a supported Download control.

**DO** follow fresh attachment hints and retain their workspace/source scope. **Check:** stale ordinals, changed workspace/media order, absent sources and conflicting observations stop without media-control input; the error supplies a reread route instead of guessing a replacement attachment.

## Saving an observed Download target

`save-media REF --output=PATH` accepts the same workspace file ID or remembered message-bound `/mN` attachment reference as `read-media`. It can also reopen an absent source when recent same-workspace remembered evidence supplies its exact message identity. The exact output file path is required; relative paths resolve from the invocation directory. Its parent must already exist and is resolved and pinned before input. The supplied basename is retained: no server filename or inferred extension replaces it. Existing files, directories and symlinks are never overwritten, including a destination created during the transfer. Preview `/pN` references and raw URLs are rejected. Format, lock-timeout, `--workspace=REF` and boolean `--original` options are supported; duplicate `--original`, value forms such as `--original=true`, paging, continuation, clipboard and UI-inspection flags are rejected before native work. Other commands reject `--original` unless it follows the literal `--` separator as positional text.

Source reopening requires verified absence in two stable current-view captures and a recent workspace/message binding. Hidden file IDs additionally need a remembered file-to-message association; current exposed file IDs retain ordinary resolution without a cache. Missing, expired, conflicting or wrong-workspace evidence stops. An already exposed source with a missing or changed attachment, a one-capture disappearance, or a failed source/control guard does not permit navigation. The helper needs an exact observed sidebar-ID route or supported channel/group ID-picker destination, verifies the actual conversation ID, finds the exact source message within its bounded lookup and re-resolves the attachment from two fresh captures. Individual DMs without an observed route stop. Older-message search additionally requires a securely verified generated scope; unsupported DM filters or unknown scope stop without a guessed replacement query. This is not universal history access. A positional reference keeps its original attachment-order binding across navigation. The cache supplies a navigation target, never a Download authorization or replacement attachment metadata. Existing source/Download/viewer verification and `--original` selection apply afterward.

Direct saving requires a supported Download AXLink in the verified media container. The observed HTTPS `files.slack.com` target must carry a matching team/file identity under `files-pri` or `files-tmb`; its exact URL is preserved. The default prefers one verified canonical private-file `/download/<basename>` route with a matching source-owned file-page identity and basename. Its optional `origin_team` query must match the current AX context; variant paths or unknown query parameters do not establish a file-content route. Distinct preferred URLs are ambiguous and stop; duplicate observations of the same URL can select one retained control. When none is exposed, the default requires a unique supported observed fallback. Add `--original` to require the preferred route and stop before Download if it is unavailable or ambiguous. A supported media kind, filename, thumbnail or file-page URL alone never authorizes input, and no URL is reconstructed. Slack's native download directory must already be configured and exist. The helper neither changes this preference nor enters a save dialog. It uses Slack's native download control and reads only the relevant directory setting and exact URL/context/file-bound download record from local persisted state; it does not extract credentials or make an independent authenticated request. The ledger bucket is bound to the fresh AX workspace or enterprise context (`T…` or `E…`); the file owner's `T…` ID in the Download URL is a separate identity and does not choose that bucket.

After one verified Download action, a fresh matching completed record and stable local file are required. A separate filesystem publisher copies at most 256 MiB, waits up to ten seconds for Slack's nonempty quarantine attribute, preserves every source extended attribute byte-for-byte, and independently checks SHA-256 and size before and after atomic no-overwrite publication. The destination parent must match the device/inode pinned by the wrapper. Only destination-only OS-added `com.apple.provenance` is allowed beyond source attributes and is listed in `systemAddedXattrs`; if provenance was already on the source, its bytes must match too. The 256 MiB limit applies to verified publication, not native network transfer: Slack may already have downloaded a larger file before its size is known. The native download is retained. The copy establishes equality with that completed Download target; a `files-tmb` target can be a rendition, and no uploaded-original or MIME-type claim follows.

When the requested source has no Download controls at all, a supported static-image gallery can instead open its file viewer in the requested interaction mode. The known file ID, retained original source, canonical image opener URL and active viewer image must agree; the viewer's cloned thread cannot replace the source. Only the Download button in that active image's media-controls footer qualifies. Unsupported, disabled, stale or ambiguous source controls do not trigger a viewer fallback. A pre-existing viewer/details pane or unsupported layout stops. The URL-less image-viewer button requires a fresh same-owner/file download record in the pinned AX context; its first observed actual URL and start time must remain unchanged. ## Existing transcript reading

`read-transcript REF` accepts the same observed workspace file ID or message-bound `/mN` attachment reference as `read-media`, with the same grammar and remembered-order protection. The selected record must be an audio or video attachment with an existing transcript control. Images, documents, external `/pN` previews, generation-only controls and unknown transcript availability do not produce a transcript-read hint. Format, lock-timeout and `--pages=N` (1–10) options are supported; `--before`, `--after`, clipboard and UI-inspection options are rejected before native work.

The helper first captures and resolves the current source/media binding. Only after that validation does the wrapper select one native candidate retained by the same helper process. A guarded existing-transcript action establishes the selected-media transition; an unrelated pre-existing panel is not read as that media’s transcript. Unsupported, stale, ambiguous or changed evidence stops without generating, playing, seeking or automatically replaying an action. The final transcript must have stable timestamp/text structure across two captures.

Successful semantic output has `operation: "read-transcript"`, the requested reference, workspace/view, `media`, `sources`, supported source navigation, and a separate `transcript` object. `transcript.segments[]` retains observed timestamp labels and text in exposed order; timestamp labels may be spoken strings such as `2 seconds`, not necessarily clocks. `transcript.text` joins the captured segment text for convenience. `transcript.contentRead` is true because those exposed words were read; `media.contentRead` remains false because no original media bytes were acquired. `coverage.complete` remains false, and an exposed final timestamp does not prove full coverage or transcription accuracy.

A verified message-bound read retains its requested reference and preflight metadata throughout the operation. Opening the panel can expose a file ID that was absent before input; this does not silently rewrite the selected ordinal. Positional transcript results offer `inspect` to refresh attachment references before another attachment read. A later call using the old ordinal still requires its remembered binding to match fresh metadata; an exposed file ID or changed media order requires a source reread. File-ID references retain their direct attachment-inspection hint.

Default text shows up to 40 segments within a 6,000-Unicode-character segment-output budget, with bounded labels/source context. It explicitly reports omitted segments or shortened text and points to `--format=json`, which retains every captured segment and its full text. Output-format flags do not scroll or fetch more transcript content. Full JSON retains preflight source captures, selected-candidate evidence, native panel captures and wrapper resolution; unsuccessful selection or verification keeps its failed status in every format. Private transcript bodies belong outside repository fixtures and documentation.

Transcript failures retain an explicitly reported `openingMayHaveBeenRequested` in compact JSON: true means token delivery may have authorized opening; false means no opening token was sent; null or absence remains unknown. Text adds the corresponding short caution or no-token statement only for a boolean value. A missing field on a known native failure never becomes false. Full JSON preserves the original protocol/native evidence, and every format retains source errors and any foreground interaction evidence without authorizing replay.

Omitted `--pages` and `--pages=1` keep the single-capture schema. With `--pages=2..10`, the first capture counts toward the budget, followed by downward captures inside the same bound transcript. Pages contain all structurally exposed segments, which can extend beyond the viewport. Collection deduplicates matching overlapping timestamp groups: timestamps are normalized to seconds for comparison, and every ordered text occurrence at that time must match. Original timestamp labels and segment text are retained from the first capture. Identical phrases at different times remain separate; multiple segments at one time are not collapsed. A partial timestamp group, changed text, missing overlap, or reordered segments stops before accepting that page.

Collections add `pagination` with `direction: "down"`, `hasMore: null`, captured/returned counts, scroll attempts represented by verified pages and a `batch` containing requested/completed/attempted page counts, duplicate count and stop reason (`page-limit`, `no-progress`, `error` or `time-limit`). A final no-progress capture counts as a completed page, with its repeated segments counted as duplicates. It does not establish an endpoint. The text limit applies to the entire collection and its summary explains an early stop. A later failed page produces `status: "partial"`, exit 1, retained verified segments and inspection guidance in all formats; a first-page failure retains ordinary stopped behavior. There are no transcript continuation cursors. Full JSON retains each native page, desktop samples, bounded after-error observations when available, and the final wrapper resolution; a failed transition can have attempted input even though it contributes no verified-page scroll count. The activity lock remains held throughout collection.

An offered existing-transcript control can open Slack's explicit unavailable state. The recognized video notice returns `stopped`, exit 1, with guidance to inspect the same media reference or choose another attachment. It never becomes a successful empty transcript. Unknown or mixed panel structures retain their ordinary refusal, and no generation or language/feedback control is pressed.

**DO** preserve the observed transcript and its selected-media binding. **DON'T** equate a control label, an old open panel or a transcription timestamp with verified content coverage. **Check:** source/media identity, existing-control selection, stable panel segments and sampled interaction/playback evidence support the returned transcript; generation and playback actions remain absent.

## Thread expansion

`read-thread REF_OR_PERMALINK` reads an already-open matching thread, or opens the unique reply control bound to an exposed message in a conversation/search view. Compact refs have the form `CONVERSATION:SECONDS.MICROSECONDS` (ten seconds digits and six microsecond digits). HTTPS Slack message permalinks are also accepted. Locate an unexposed message with `search`, `read-channel` or `read-dm` first; the command does not open external URLs or search arbitrary URLs as a navigation substitute.

The result contains `thread: {ref, requestedMessageTS, rootTS, rootPermalink, displayedReplyCount, observedReplyCount, capturedReplyCount, root, replies}`. `root` and `replies` use the message-record fields above and are always separate. When no verified capture exposes root text, `root` is null and its observed permalink remains available alongside verified replies. A multi-page collection retains an exposed root once even if later pages virtualize it away. A reply permalink can be read when its addressed message is initially present in the open thread; later pages follow the verified root. Both the addressed message identity and thread root are verified. All timestamps remain strings. Unknown authors/times/links remain null.

Plain text keeps one root section with its text or an outside-view note and source link, then up to ten replies per logical page, each capped at 500 characters. JSON retains the same selected replies with full captured text. `displayedReplyCount` is Slack's exposed count or null; `observedReplyCount` counts selected replies returned and `capturedReplyCount` counts captured replies, unique across verified pages for a collection. Matching counts still do not prove complete thread content. Surrounding channel messages, composer content and attachments' contents are excluded. An initially empty thread requires explicit zero-reply evidence; missing/loading replies produce a useful stop instead. An empty continuation page is labeled `no-progress` rather than an empty thread.

## Search and inspection

Search output includes `search: {query, totalResults, page, pageCount}` and captured `messages` with `snippet: true`. Each snippet retains its observed channel label and source permalink where available. Counts describe the displayed search results, not the number of full messages read. Empty results require the dedicated empty-state UI; an unavailable result list is not treated as zero matches.

When a public `search` request contains supported Unicode emoji, the wrapper translates whole emoji graphemes to explicit Slack shortcodes before native input. Both JSON formats add top-level `searchTranslation: {requestedQuery, submittedQuery, substitutions: [{unicode, shortcode}]}`. Substitutions retain occurrence order. The original request stays separate from `search.query`, which remains the submitted query observed in Slack; every page is independently checked against that submitted string. The wrapper recomputes the deterministic translation before attaching the annotation. Translation metadata is retained on failures and does not establish successful submission or verified results. Full JSON still preserves the native diagnostic receipt and status. Text adds a bounded `Emoji query: REQUEST → SUBMITTED` note; ordinary queries retain their existing output. Unsupported sequences, unsupported emoji-bearing filters and invalid translated queries stop before native input rather than accepting an approximate match.

`search QUERY --pages=N` (1–10) submits the query once, then collects consecutive actual result pages using one scoped, advertised `Next page` AXPress per transition. Slack normally exposes twenty matches per result page; each captured frame is bounded to at most 100 matches. This is independent of the ten-record logical pages used for conversations. Search does not accept `--before` or `--after`, and no cursor or executable next-page navigation action is fabricated.

The query, workspace, exposed filter/sort controls and displayed page count must stay consistent, and each verified page must advance consecutively. Hidden filter values remain unknown: the receipt is not a complete filter-state audit. A missing or changed control, query, exposed scope or page identity stops collection; an uncertain Next page press is never repeated automatically. The collection retains the original app/window and foreground baseline, uses the same 60-second native continuation budget and 90-second wrapper deadline, and adds no activation, focus-setting, mouse or keyboard primitive.

Full receipts preserve real empty IDs for the two supported passive controls, `Reset` and `Give feedback`, rather than inventing IDs or omitting them. Their exact role, label, value, selected state, classes and verified placement distinguish them; duplicate or unknown idless controls still stop. Scope arrays sort by ID then label and retain both controls for unchanged-state comparison across pages. They are never pagination input targets.

Search aggregation preserves Slack's result order. It deduplicates by canonical observed message-permalink identity and retains the first whole record, without combining body or metadata across pages. Identical text in different messages remains distinct. JSON retains every unique collected match; text shows the first `10 × completedPages` matches, caps each body at 500 characters, and labels both omitted matches and shortened text. The original single-page behavior remains unchanged when `--pages` is omitted or equals one.

For a collection, `search.firstPage` and `search.lastPage` identify the verified page range when exposed; `search.page` is the last verified page. `pagination.supported` is true, `direction` and `batch.direction` are `next`, and `nextCursor` is null. `hasMore` derives from the final displayed page/page-count comparison, with false also supported by verified empty results; otherwise absent evidence or a partial error leaves it null. `capturedCount` counts raw verified match observations before deduplication, `returnedCount` counts unique collected matches, and `batch.deduplicatedCount` counts repeated matches removed. `pressAttempts` counts only transitions represented by verified frames; `batch.attemptedPages` also includes later failed transition attempts. `coverage.complete` remains false and every message retains `snippet: true`, even at the last displayed result page.

The same multi-page full-JSON envelope contains individual raw search receipts under `pages` plus `batch` metadata. A later native or semantic failure retains only the verified prefix with `status: partial` and exit 1; default text keeps those matches before its stop notice. Explicit empty results are a normal verified empty frame followed by `no-next-page`, not a failure or retry. Result-page completion never proves full message or thread contents were read.

Inspection of an open picker returns `query: {value, suggestions}` with observed labels/handles, without reading an underlying conversation through the overlay. Unsupported views return a narrow view summary and coverage warning; full JSON remains available for diagnosis.

## UI inspection

`inspect --ui` is an explicit diagnostic mode; ordinary `inspect` retains its semantic output. The default performs AX reads only. `--prepare` requests the existing bounded runtime accessibility initialization before reading; it adds no navigation, focus-setting, arbitrary AX action or permission grant. The flags `--limit=N`, `--depth=N` and `--prepare` require `inspect --ui`; `--filter=TEXT` is also supported by `dms` with the distinct meaning described above. The UI filter accepts at most 200 Unicode characters without control characters and performs a literal case-insensitive substring match over bounded role/subrole, ID, classes and label. It does not search values or capability names. Empty means all inspected nodes. Limits accept 1–500 nodes (default 80), depth accepts 0–40 (default 20), and ancestors count toward the result limit. If a match plus its ancestors cannot fit, zero returned nodes is possible without proving no matches exist.

Text shows the capture interval and identity comparison, counts/limits, then capture-local indices, parent indices, roles, labels, IDs, known state, advertised actions, settable attributes and bounds. Metadata shortening is labeled; JSON retains all returned fields. Capabilities have no corresponding arbitrary input subcommand. A numeric node index cannot be reused as a stable selector in a later capture.

The diagnostic JSON envelope is `{schemaVersion: 1, operation: "inspect", mode: "ui", pid, ui}`. The `ui` object has these fields:

| Field | Meaning |
|---|---|
| `captureId`, `captureStartedAt`, `observedAt` | UUID and start/end timestamps for this bounded capture; contents can change during or after the interval |
| `root` | `kind` workspace/application, selection reason, before/after role/title/URL/window identity, and nullable `viewIdentityMatched`; equal boundary identities do not prove unchanged contents |
| `preparation` | Whether preparation was explicitly requested and its recorded steps; false has no preparation steps |
| `nodes` | Selected nodes in observed depth-first order, with all retained ancestors and original, possibly nonconsecutive, capture indices |
| `coverage` | Selection/filter/limit/depth, visited/matched/returned/redacted counts, AX read counts, read/time budgets, `scanComplete`, `truncated`, reasons and `complete: false` |

Each node contains `index`, `parent`, `depth`, `matched`, `role`, `subrole`, `id`, `classes`, nullable `label`/`value`/`url`, `actions`, `attributeNames`, `settableAttributeNames`, `unknownSettableAttributeNames`, nullable `enabled`/`focused`/`selected`/`expanded`, nullable `{x,y,width,height}` bounds, `redacted` and `contentOmitted`. `matched: false` denotes retained ancestor context. Null capability arrays mean unavailable; empty arrays mean an observed empty list. Unknown state remains null, not false. Settable attributes and unknown settable checks are disjoint subsets of observed attribute names.

Composer, editable text-area and secure subtrees expose a redacted structural node with null content and no descendants. Failed role/subrole/class reads leave classification unknown and produce the same structural-only boundary with `redacted: "unreadable-content"`; missing discrimination is never permission to read content. Structural containers omit aggregate labels/values/URLs while retaining child traversal (`contentOmitted: "aggregate-content"`). Recognized view containers and lists may retain their own title/description but omit aggregate value/URL (`"aggregate-value"`). This avoids recovering draft or message content through an ancestor's aggregate text. A diagnostic inspection is still private UI evidence, not a shareable sanitized transcript.

Traversal is bounded to 5,000 visited nodes, 12,000 AX read operations and an eight-second budget; each AX call also has a bounded timeout. Native string/array caps are separate from the result limit. Strings cap at 1,000 Unicode characters, roles/subroles at 128, classes at 128 entries of at most 256 characters, and capability lists at 128 entries of at most 128 characters. `truncatedFields` identifies clipped node/root metadata. Counts describe inspected nodes only and are never estimates of the entire app. `scanComplete` describes traversal within the exposed root, while `complete` remains false. Field/capability clipping can coexist with completed traversal. Reasons distinguish result, depth, traversal, operation, deadline, root-selection, AX-read, field/capability and redaction limits.

Native element identity, rather than labels or DOM IDs, deduplicates repeated child references. Optional `coverage.repeatedReferences` counts references skipped during diagnostic traversal; `coverage.rootRepeatedReferences` sums those skipped during the before/after workspace-root discovery passes. Both are nonnegative integers, with zero distinct from an absent field in older receipts. Repeats alone do not imply truncated traversal. Existing application windows are also read from `AXWindows` and combined by native identity with the child inventory; no window is opened, raised or selected. Full message captures add `content.repeatedReferences`. A table cell already captured under its canonical row may also appear through a column or verified header of that same table; the helper preserves the first occurrence only after verifying stored ancestry and live roles and parent identities. Header groups additionally require exact AXHeader identity and unique membership in AXColumnHeaderUIElements. Other conflicting non-cyclic ancestry fails capture rather than assigning content to an arbitrary message.

An ancestry failure may add `captureConflict` to full JSON. It records bounded role/DOM-ID/class descriptors for the repeated node, both traversal parents, up to eight stored ancestors per parent, and the actual AXParent comparison or exact AX error. A failed table-header proof can add typed header/membership status and comparison booleans. Unknown parent comparisons are null. Truncation is explicit. These descriptors omit labels, values and URLs; they diagnose the stopped capture and do not authorize selection or establish a valid message source. Default text and compact JSON retain their concise error behavior.

A rejected Search suggestion can add `pickerStructure` to failed full JSON before recovery closes the picker. It records only roles, classes, actions, parent indexes, child counts and enabled/focused states, bounded to 12 nodes, depth three and one second. Labels, values, IDs and URLs are excluded; unavailable fields remain null and limits are explicit. This diagnostic does not authorize navigation or relax destination verification.

`content.tableCellProjections` counts only repeated cells accepted by the canonical row/same-table rule; `content.tableHeaderProjections` counts the subset verified through the table’s explicit header attributes. Zero means the rule was not exercised in that capture; absence in an older receipt is unknown. This full-JSON diagnostic does not change message counts or imply complete table or history coverage.

Root selection falls back to an application inventory when the workspace is absent, ambiguous or selection is incomplete. `viewIdentityMatched` can be false or unavailable; diagnostic output remains useful and reports that limit. No successful diagnostic capture establishes current-state truth after completion, an atomic snapshot, or permission to act on stale references. Full JSON keeps the original native receipt even when diagnostic validation rejects it.

## Errors and filtering

Text/compact JSON exit 0 means the requested semantic structure and destination were verified, or inspection returned an explicitly limited view summary. Full JSON preserves the native exit status without requiring semantic extraction. Exit 1 indicates a stopped operation; inspect its error and current state before deciding on another operation. Exit 2 is CLI usage/platform failure. Exit 3 means Accessibility trust or target AX access is missing in that invocation; verify approved execution context before concluding that macOS setup is required. Native errors and permission guidance use the selected output format; plain-text failures go to stderr, while JSON error objects go to stdout. A failed selection leaves the search overlay available for inspection and never retries Return automatically.

Cooperating commands wait for the activity lock for up to 30 seconds by default; `--lock-timeout=N` accepts an integer from 0 to 120, with zero requesting an immediate contention result. Waiting is cancellable and does not start a native helper. Lock failures retain ordinary stopped output and add a bounded `lock` object: `path`, `reason`, `waitedMs`, `timeoutSeconds`, `ownerStatus`, nullable `ownerPid`/`operation`/`acquiredAt`, `processState`, and scope `cooperating helper processes only`. Owner metadata excludes queries, targets and ownership tokens. A running PID is only process-liveness evidence, not proof of helper identity, lock ownership or Slack UI state. Legacy, missing, malformed or unreadable owner metadata is explicit; no automatic lock takeover follows.

A native stopped operation or partial collection can add `observation: {phase: "after-error", readOnly: true, expectedScope, ui}`. The optional scope contains the operation and, when established, the pinned `/client/ID` workspace context; it does not claim the initial full view URL was the expected navigation destination. This fresh diagnostic attempt uses a two-second budget, at most 60 returned nodes, depth 30 and control-oriented selection. It performs no preparation or navigation. Text appends at most six useful named controls, the actual observed view and an `inspect --ui` hint; JSON retains the validated bounded observation. It is after-error evidence, not proof of cause. Invalid/unavailable diagnostics do not replace the original error, exit code or verified collection prefix.

For `--pages=N` greater than one, a later native or semantic failure retains only the previously verified pages with `status: partial`, `error`, `next` and exit 1. Text displays its bounded selection followed by the stop notice; compact JSON retains every collected record. Conversation/thread pagination hints are null because the final current view may no longer be verified; sidebar/search collections never fabricate continuation hints. A first-page failure returns the ordinary error without collected content. A native time-budget stop also retains prior verified pages with exit 1; a hard process deadline or invalid native receipt can prevent partial-content recovery. Inspect the actual result before resuming, and do not automatically replay navigation.

Individual-DM destination failures may return `status: "ambiguous"` or `"not-found"` with exit 1, the requested `query`, `error`, `next`, `candidates`, `candidateCount`, `candidatesTruncated` and `exactMatchCount`. No destination was selected by that failed lookup. Each candidate contains `{name, handle, navigation}` from the verified current picker or direct-search list; only a single observed handle unique among the available person suggestions receives a navigation command. Normal-picker commands use `{command: "read-dm", args: [handle]}`; direct-search commands use `[handle, "--allow-clipboard"]` to retain the required opt-in. Missing, conflicting or duplicated handles leave `navigation: null`. Query, quick-message and group suggestions are excluded from person candidate commands.

`exactMatchCount` distinguishes zero exact matches from exact-name ambiguity; multiple approximate candidates alone cannot authorize selection. An eligible normal failure without clipboard opt-in offers a same-target retry with `--allow-clipboard`. Direct-search fallback requires every advertised ARIA position and size before unique selection; incomplete coverage returns `stopped` with bounded observed-person candidates and direct-search `--allow-clipboard` actions, not a false `not-found` or uniqueness claim. Unsupported UI, changed identity, failed post-selection verification or absent message timestamp identity also return a stopped read without a guessed conversation ID. Successful fallback adds only the optional `lookup` metadata to semantic JSON; text stays focused on messages and full JSON retains native recovery/target evidence.

Text says “Choose an available candidate” and shows up to eight rows with safe argument quoting. JSON retains the native cap of twenty candidates; `candidateCount` counts all available DM suggestions and `candidatesTruncated` records when that cap omitted some. Candidates can be approximate name suggestions, so neither their presence nor their order authorizes an automatic selection. Use the intended person's observed identity to choose a command. If no candidates are available, check the name or workspace; the helper does not substitute a fuzzy destination.
